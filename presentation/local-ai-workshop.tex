\begin{frame}{Model size is not the same as inference cost}
\small
\lead{Dense small model $\to$ sparse MoE $\to$ very large sparse MoE}
\par\medskip
\begin{tabularx}{\textwidth}{@{}>{\raggedright\arraybackslash}p{0.35\textwidth}Y Y@{}}
\toprule
\textbf{Model} & \textbf{Total parameters} & \textbf{Active/effective}\newline\textbf{per token} \\
\midrule
Gemma 4 E4B (dense) & $\sim$8B incl.\ embeddings & $\sim$4.5B effective \\
\addlinespace[0.5em]
Gemma 4 26B A4B (MoE) & $\sim$25.2B & $\sim$3.8--4B active \\
\addlinespace[0.5em]
DeepSeek V4 Flash (MoE) & $\sim$284B & $\sim$13B active \\
\bottomrule
\end{tabularx}
\par\medskip
\textbf{Total} describes stored model capacity. \textbf{Active/effective}
better indicates per-token computation, but does not determine tokens/s alone.
\par\medskip
\textbf{Gemma 26B can be faster than E4B:} mixture of experts (MoE) selects
only $\sim$4B parameters per token. The full 26B is not evaluated each time.
\par\medskip
\textbf{DeepSeek:} $\sim$284B parameters of model capacity, $\sim$13B active per token.
\source{E4B is dense, not MoE. Its large embedding tables use lookups, explaining the effective count.
Parameter counts are approximate, not FLOP or speed measurements.
Sources: \href{https://ai.google.dev/gemma/docs/core/model_card_4}{Google Gemma 4 model card};
\href{https://api-docs.deepseek.com/news/news260424/}{DeepSeek V4 release}.}
\note{Architecture sources checked 26 October 2026:
\url{https://ai.google.dev/gemma/docs/core/model_card_4};
\url{https://api-docs.deepseek.com/news/news260424/}.
Google lists E4B under dense models: 4.5B effective parameters, 8B with
embeddings. Per-Layer Embeddings use lookups; effective does not mean MoE
expert routing. The text-model counts do not include the additional multimodal encoders.
Gemma 4 26B A4B has 25.2B total and 3.8B active parameters, often rounded to 4B.
DeepSeek V4 Flash's release specifies 284B total and 13B active.
The progression is E4B, 26B A4B, then DeepSeek V4 Flash.
Sparse activation explains why more total parameters need not mean more
computation per token. It makes higher throughput for Gemma 26B than E4B
plausible, but these observations do not isolate architecture as the cause.
Memory bandwidth, attention, context length, kernels, quantization and distributed
communication also affect cost. Active counts neither specify exact FLOPs nor
guarantee dense-model-equivalent quality or speed. Total weights still impose
storage and deployment memory requirements, even when a token uses a subset.}
\end{frame}

\bottomrule
\end{tabularx}
\par\medskip
\begin{itemize}
\setlength{\itemsep}{0.35em}
\item \textbf{Serving stacks, hardware, formats and quantization differ.}
\item \textbf{Tokenizers and reasoning differ,} so token counts are not equivalent.
\end{itemize}
\note{Gemma E4B uses mlx-community/gemma-4-e4b-it-4bit via vLLM Metal
on the M1 Pro. Gemma 4 26B A4B uses gemma4:26b via Ollama on the same
hardware class. DeepSeek V4 Flash uses vLLM across the two DGX Spark nodes.
The historical snapshot does not pin enough runtime versions and exact
Ollama/DeepSeek quantization metadata to reproduce a controlled comparison.
Do not infer identical precision from a model name or fill in an unrecorded quantization.
Historical API output limits were 150, 800 and 800 respectively. E4B's finish
reasons were not saved, but its quantum, robotics and Inception answers visibly
end at 150 completion tokens. Ollama has two length finishes; DeepSeek has none.
The current Ollama notebook records 163.027698 completion tokens/s and uses
MAX\_TOKENS = 1280. Its numerator is API usage.completion\_tokens, including
reasoning-generation tokens, not a separately measured count of visible-answer tokens.
The historical snapshot also lacks separate reasoning-token counts, so neither
the old nor new figures support a normalized visible-output speed ranking.
To isolate effects, match hardware, runtimes where possible, precision, prompts,
output limits, reasoning settings and token accounting, and repeat measurements.
The workshop instead illustrates practical local deployment trade-offs.}
\end{frame}

\note{Slide 13 follows the RAG architecture with an embedding-space explanation.
First explain an embedding as a list of numbers, interpreted as coordinates in
a high-dimensional space. Similar meanings tend to be nearby; some learned
directions express relationships. 3Blue1Brown illustrates this using

that the analogy is imperfect. E denotes the embedding function. These are word-embedding intuitions, not a guarantee
that all embedding models obey semantic arithmetic.
Ask the audience: Holland + Fries - Kroket is approximately which country?

replaces kroket with fries while retaining the country role. The coordinates and
snack associations are invented to illustrate the vector operation, not measured

exactly the same displacement in this toy diagram. The real space has many more
than two dimensions, and analogy results need not land exactly on a word vector.
EmbeddingGemma embeds whole questions and document chunks for retrieval, rather
than merely looking up individual token vectors. Query and document encoding
use the model's respective task prompts and produce vectors in a shared space.
Retrieval ranks passages by vector similarity; it does not require snack-style
vector arithmetic. Both overlay pages retain logical slide number 14 of 15.
